## Сценарий 1: Первая доставка feature

### Контекст
Вы завершили разработку новой функциональности в feature ветке и готовы создать PR.

### Шаги

```bash
# 1. Проверяем текущее состояние
$ git status
На ветке tasks/PROJ-100/PROJ-101
нечего коммитить, нет изменений в рабочем каталоге

# 2. Запускаем доставку
$ git-flow-helper deliver

=== ДОСТАВКА FEATURE ===

--- Выбор целевой ветки ---
1) test (обычный сценарий)
2) release_oe
3) release_pe
Выберите целевую ветку [1-3]: 1

=== ВЫБОР КОММИТОВ ===
Последние коммиты:
--------------------
[1] abc1234 feat: Добавлен новый компонент Dashboard
[2] def5678 fix: Исправлена валидация формы
[3] ghi9012 refactor: Оптимизирован запрос к БД
[4] jkl3456 test: Добавлены unit-тесты для Dashboard
--------------------

? Выберите коммиты для доведения: all

--- Работа со stable веткой ---
ℹ Создание новой ветки tasks/PROJ-100/stable_PROJ-101 от master

--- Cherry-pick коммитов ---
ℹ Перенос коммита jkl3456
ℹ Перенос коммита ghi9012
ℹ Перенос коммита def5678
ℹ Перенос коммита abc1234
ℹ Отправка stable ветки

? Хотите объединить коммиты в stable ветке? (y/n) y
? Введите сообщение для объединенного коммита:
feat: Dashboard component with validation fixes and optimizations

--- Работа с merge веткой ---
ℹ Создание новой ветки tasks/PROJ-100/test_PROJ-101 от test

--- Слияние со stable веткой ---
ℹ Отправка merge ветки

=== ЗАВЕРШЕНО ===
✔ Доставка успешно завершена!

Stable ветка: tasks/PROJ-100/stable_PROJ-101
Merge ветка для PR: tasks/PROJ-100/test_PROJ-101 -> test

Теперь создайте Pull Request:
tasks/PROJ-100/test_PROJ-101 → test
```

### Результат
- Создана stable ветка с объединенным коммитом
- Создана merge ветка готовая для PR
- Можно идти в GitHub/GitLab и создавать PR

## Сценарий 2: Доработка после code review

### Контекст
После code review нужно внести изменения в уже существующий PR.

### Шаги

```bash
# 1. Вносим изменения в feature ветке
$ git add .
$ git commit -m "fix: Исправления по code review"

# 2. Обновляем PR
$ git-flow-helper

╔══════════════════════════════════════════════╗
║         Git Flow Helper - v2.0               ║
╚══════════════════════════════════════════════╝

Текущая ветка: tasks/PROJ-100/PROJ-101

=== Feature ветка ===
1) Доставить изменения (deliver)
2) Обновить существующий PR

Выберите действие: 2

=== ОБНОВЛЕНИЕ PULL REQUEST ===

--- Поиск существующих PR ---
ℹ Найден PR: tasks/PROJ-100/test_PROJ-101 -> test

=== ВЫБОР КОММИТОВ ===
Последние коммиты:
--------------------
[1] xyz7890 fix: Исправления по code review
[2] abc1234 feat: Dashboard component (squashed)
--------------------

? Выберите коммиты для доведения: 1

--- Обновление stable ветки ---
ℹ Перенос коммита xyz7890

--- Пересоздание merge ветки ---
⚠ Удаление старой merge ветки
ℹ Создание новой merge ветки от test

--- Слияние со stable веткой ---
ℹ Обновление PR (force push)

=== ЗАВЕРШЕНО ===
✔ PR успешно обновлен!

Обновленная ветка: tasks/PROJ-100/test_PROJ-101 -> test
```

### Результат
- PR обновлен новыми изменениями
- История обсуждений в PR сохранена
- Reviewers увидят новые изменения

## Сценарий 3: Срочный HotFix в production

### Контекст
Обнаружен критический баг в production версии, нужно срочно выпустить патч.

### Шаги

```bash
# 1. Сначала фиксим баг в основной ветке
$ git checkout test
$ git pull origin test
# ... вносим исправления ...
$ git add .
$ git commit -m "fix: Критическое исправление NPE в платежном модуле"
$ git push origin test

# 2. Создаем HotFix
$ git-flow-helper hotfix

=== СОЗДАНИЕ HOTFIX ===

--- Выбор версионной ветки ---
1) PE (versions/pe/XX.XX.XX.X)
2) OE (versions/oe/XX.XX.XX.X)
3) IZ (versions/iz/XX.XX.XX.X)
Выберите тип [1-3]: 1

--- Доступные версии ---
1  versions/pe/02.01.00.0
2  versions/pe/02.01.01.0
3  versions/pe/02.02.00.0  ← текущая в production
Выберите версию: 3

? Введите номер JIRA задачи: HOTFIX-911

ℹ Версионная ветка: versions/pe/02.02.00.0
ℹ Hotfix ветка: hotfixes/pe/HOTFIX-911

--- Выбор источника коммитов ---
1) test
2) release_oe
3) release_pe
4) Текущая ветка
Откуда взять коммиты? [1-4]: 1

=== ВЫБОР КОММИТОВ ===
Последние коммиты:
--------------------
[1] aaa1111 fix: Критическое исправление NPE в платежном модуле
[2] bbb2222 feat: Новая фича (не для hotfix)
--------------------

? Выберите коммиты: 1

--- Создание hotfix ветки ---
ℹ Создание новой ветки hotfixes/pe/HOTFIX-911 от versions/pe/02.02.00.0

--- Cherry-pick коммитов ---
ℹ Перенос коммита aaa1111
ℹ Отправка hotfix ветки

=== ЗАВЕРШЕНО ===
✔ Hotfix успешно создан!

Hotfix ветка для PR: hotfixes/pe/HOTFIX-911 → versions/pe/02.02.00.0

Теперь создайте Pull Request:
hotfixes/pe/HOTFIX-911 → versions/pe/02.02.00.0
```

### Результат
- Создан hotfix для production версии
- После мержа PR можно сразу выкатывать патч

## Сценарий 4: Работа с конфликтами

### Контекст
При доставке возникли конфликты из-за параллельных изменений.

### Шаги

```bash
# 1. Начинаем доставку
$ git-flow-helper deliver

=== ДОСТАВКА FEATURE ===
# ... выбор веток и коммитов ...

--- Cherry-pick коммитов ---
ℹ Перенос коммита abc1234
⚠ Конфликт при cherry-pick коммита abc1234

✗ ОБНАРУЖЕН КОНФЛИКТ!
1. Разрешите конфликт вручную
2. Выполните: git add <файлы>
3. Запустите: git-flow-helper --continue

# 2. Смотрим конфликты
$ git status
На ветке tasks/PROJ-100/stable_PROJ-101
Вы сейчас отменяете коммит.

Не слитые пути:
  (используйте «git add <файл>...» для разметки разрешения)
    оба изменены:   src/components/Dashboard.jsx

# 3. Разрешаем конфликты в редакторе
$ vim src/components/Dashboard.jsx
# ... правим конфликты ...

# 4. Добавляем разрешенные файлы
$ git add src/components/Dashboard.jsx

# 5. Продолжаем доставку
$ git-flow-helper continue

=== ПРОДОЛЖЕНИЕ ДОСТАВКИ ===
ℹ Восстановлено состояние:
  Действие: deliver_feature
  Feature ветка: tasks/PROJ-100/PROJ-101
  Stable ветка: tasks/PROJ-100/stable_PROJ-101
  Merge ветка: tasks/PROJ-100/test_PROJ-101

✔ Cherry-pick завершен
ℹ Отправка stable ветки

--- Работа с merge веткой ---
ℹ Создание новой ветки tasks/PROJ-100/test_PROJ-101 от test

--- Слияние со stable веткой ---
# Если снова конфликт:
⚠ Конфликт при merge

✗ ОБНАРУЖЕН КОНФЛИКТ!
1. Разрешите конфликт вручную
2. Выполните: git add <файлы>
3. Запустите: git-flow-helper --continue

# 6. Разрешаем merge конфликты
$ git status
$ vim src/components/Dashboard.jsx
$ git add .
$ git commit

# 7. Завершаем доставку
$ git-flow-helper continue

=== ПРОДОЛЖЕНИЕ ДОСТАВКИ ===
✔ Merge завершен
ℹ Отправка merge ветки

=== ЗАВЕРШЕНО ===
✔ Доставка успешно завершена!
```

### Результат
- Все конфликты разрешены
- Изменения успешно доставлены
- Состояние автоматически восстановлено после каждого этапа

## Сценарий 5: Доставка в release ветки

### Контекст
Фича готова и нужно довести её сразу в release_oe для тестирования.

### Шаги

```bash
# 1. Запускаем доставку с выбором целевой ветки
$ git-flow-helper deliver

=== ДОСТАВКА FEATURE ===

--- Выбор целевой ветки ---
1) test (обычный сценарий)
2) release_oe  ← выбираем для опытной эксплуатации
3) release_pe
Выберите целевую ветку [1-3]: 2

ℹ Feature ветка: tasks/PROJ-100/PROJ-101
ℹ Stable ветка: tasks/PROJ-100/stable_PROJ-101
ℹ Merge ветка: tasks/PROJ-100/release_oe_PROJ-101  ← другое имя
ℹ Целевая ветка: release_oe

=== ВЫБОР КОММИТОВ ===
# ... выбор коммитов ...

--- Работа со stable веткой ---
# ... cherry-pick как обычно ...

--- Работа с merge веткой ---
ℹ Создание новой ветки tasks/PROJ-100/release_oe_PROJ-101 от release_oe

--- Слияние со stable веткой ---
ℹ Отправка merge ветки

=== ЗАВЕРШЕНО ===
✔ Доставка успешно завершена!

Merge ветка для PR: tasks/PROJ-100/release_oe_PROJ-101 -> release_oe
```

### Результат
- Создан PR напрямую в release_oe
- Минуя test ветку для срочных изменений
- Подходит для критических фиксов

## 💡 Советы по использованию

### Когда использовать каждый сценарий

| Сценарий | Когда использовать |
|----------|-------------------|
| **Первая доставка** | Завершена разработка новой фичи |
| **Обновление PR** | Нужны доработки после review |
| **HotFix** | Критический баг в production |
| **Работа с конфликтами** | Параллельная разработка в команде |
| **Доставка в release** | Срочные изменения или специальные требования |

### Лучшие практики

1. **Всегда проверяйте состояние перед началом:**
   ```bash
   git-flow-helper status
   ```

2. **Используйте squash для чистой истории:**
   - Объединяйте мелкие коммиты в stable ветке
   - Оставляйте детальную историю в feature ветке

3. **При конфликтах:**
   - Не паникуйте - состояние сохранено
   - Внимательно разрешайте конфликты
   - Используйте `--continue` для продолжения

4. **Для HotFix:**
   - Сначала фиксите в основной ветке
   - Потом cherry-pick в версионную
   - Всегда тестируйте перед релизом

5. **Обновление PR:**
   - Не создавайте новый PR
   - Используйте функцию обновления
   - Force push безопасен для PR веток
