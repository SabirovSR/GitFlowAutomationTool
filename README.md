# GitFlow Automation Tool v2.0

Плагин для git bash, автоматизирующий работу с корпоративным GitFlow процессом. Включает интерактивное меню, автоматизацию доставки изменений (delivery), работу с hotfix и продолжение после конфликтов.

## ✨ Возможности

### 🎯 Основные функции

- **Интерактивное меню** - удобный выбор действий в зависимости от контекста
- **Автоматизация delivery** - полная автоматизация процесса доставки изменений
- **Выбор количества коммитов** - возможность довести несколько коммитов сразу
- **Фильтрация merge-коммитов** - автоматическое исключение merge-коммитов при cherry-pick
- **Обновление PR** - автоматическое обновление Pull Request при доработках
- **Продолжение после конфликтов** - умное сохранение состояния и продолжение операций
- **Работа с hotfix** - упрощенная работа с версионными ветками
- **Squash коммитов** - автоматическое объединение коммитов в stable ветке

### 🔄 Поддерживаемые сценарии

1. **Стандартная доставка в test** - основной сценарий разработки
2. **Доставка в release_oe** - доведение изменений до опытной эксплуатации
3. **Доставка в release_pe** - доведение изменений до промышленной эксплуатации
4. **Hotfix для версионных веток** - исправления для конкретных версий

## 🚀 Установка

### Автоматическая установка

```bash
# Клонируйте репозиторий
git clone <repository-url>
cd git_plugin

# Запустите скрипт установки
./install.sh
```

Скрипт автоматически:
- Скопирует файлы в `~/.local/bin/`
- Сделает их исполняемыми
- Предложит добавить путь в PATH (если необходимо)

### Ручная установка

```bash
# Скопируйте файлы в директорию из PATH
cp git-flow* ~/.local/bin/

# Сделайте их исполняемыми
chmod +x ~/.local/bin/git-flow*

# Убедитесь, что ~/.local/bin в PATH
export PATH="$HOME/.local/bin:$PATH"
# Добавьте эту строку в ~/.bashrc для постоянного использования
```

### Проверка установки

```bash
git flow help
```

Если команда работает - установка прошла успешно! 🎉

## 🌳 Структура GitFlow

### Основные ветки

| Ветка | Назначение |
|-------|-----------|
| `master` | Ветка стабилизации |
| `test` | Ветка разработки |
| `release_oe` | Опытная эксплуатация |
| `release_pe` | Промышленная эксплуатация |

### Feature ветки

Для каждой задачи создается набор веток:

```
tasks/PARENT_JIRA/JIRA                 # Основная ветка разработки (от test)
tasks/PARENT_JIRA/stable_JIRA          # Ветка стабилизации (от master)
tasks/PARENT_JIRA/test_JIRA            # Merge ветка для PR в test
tasks/PARENT_JIRA/release_oe_JIRA      # Merge ветка для PR в release_oe
tasks/PARENT_JIRA/release_pe_JIRA      # Merge ветка для PR в release_pe
```

**Пример:**
```
tasks/PROJ-123/TASK-456                # Feature ветка
tasks/PROJ-123/stable_TASK-456         # Stable ветка
tasks/PROJ-123/test_TASK-456           # Merge ветка
```

### Hotfix ветки

Для исправлений в версионных ветках:

```
hotfixes/pe/JIRA                       # Hotfix для PE
hotfixes/oe/JIRA                       # Hotfix для OE
hotfixes/iz/JIRA                       # Hotfix для IZ
```

### Версионные ветки

```
versions/pe/00.00.00.0                 # Промышленная эксплуатация
versions/oe/00.00.00.0                 # Опытная эксплуатация
versions/iz/00.00.00.0                 # Испытания
```

## 💻 Использование

### Интерактивное меню

Просто выполните:

```bash
git flow
```

Откроется интерактивное меню с доступными действиями. Меню автоматически определяет контекст и показывает только релевантные опции.

**Возможности меню:**
- Начать доставку изменений
- Создать новую feature ветку
- Работа с hotfix
- Продолжить после конфликтов
- Показать статус операции
- Справка

### Доставка изменений (Delivery)

#### Базовое использование

```bash
# Находясь в feature ветке tasks/PARENT_JIRA/JIRA
git flow deliver
```

#### Что происходит при доставке:

1. **Проверка изменений** - проверяется наличие незакоммиченных изменений
2. **Парсинг ветки** - извлекается PARENT_JIRA и JIRA из названия ветки
3. **Выбор коммитов** - вы выбираете, сколько коммитов нужно довести
4. **Выбор окружения** - test, release_oe или release_pe
5. **Stable ветка:**
   - Создается или обновляется `tasks/PARENT_JIRA/stable_JIRA`
   - Cherry-pick выбранных коммитов (исключая merge-коммиты)
   - Опциональный squash всех коммитов
   - Push в удаленный репозиторий
6. **Merge ветка:**
   - Создается или обновляется merge ветка
   - Merge stable ветки
   - Push с возможностью обновления PR
7. **Возврат** на исходную ветку

#### Выбор количества коммитов

При запуске delivery вы увидите список коммитов и варианты выбора:

```
Сколько последних коммитов нужно довести?
Введите число или 'all' для всех коммитов:
> 3
```

- **Число (например, 3)** - доведет последние N коммитов
- **all** - доведет все коммиты с момента ответвления от master

**Важно:** Merge-коммиты автоматически исключаются!

#### Обновление существующего PR

Если merge ветка уже существует в удаленном репозитории:

```
Ветка tasks/PROJ-123/test_TASK-456 уже существует в удаленном репозитории
Это означает, что PR уже создан.

Выберите действие:
  1) Обновить PR (пересоздать ветку с актуальной test)
  2) Продолжить с текущей веткой (добавить изменения)

Ваш выбор [1-2]: 1
```

- **Вариант 1** - полностью пересоздает ветку (рекомендуется при небольших доработках)
- **Вариант 2** - добавляет новые коммиты к существующим

#### Squash коммитов

После cherry-pick вы можете объединить все коммиты в один:

```
Хотите объединить все коммиты в один (squash)? (рекомендуется)
[Y/n]: Y

Введите сообщение для объединенного коммита:
(оставьте пустым для автогенерации)
> [PROJ-123][TASK-456] Реализация новой функциональности
```

**Рекомендуется** использовать squash для чистоты истории в stable ветке.

### Работа с Hotfix

#### Создание hotfix ветки

```bash
git flow hotfix create
```

Интерактивный процесс:

1. **Выбор типа hotfix:**
   ```
   Выберите тип hotfix:
     1) PE (Промышленная эксплуатация)
     2) OE (Опытная эксплуатация)
     3) IZ (Испытания)
   
   Ваш выбор [1-3]: 1
   ```

2. **Ввод версии:**
   ```
   Введите версию (например, 01.02.03.4):
   > 01.05.12.3
   ```
   Формат: **XX.XX.XX.X**

3. **Ввод JIRA:**
   ```
   Введите номер JIRA задачи (например, TASK-123):
   > HOTFIX-789
   ```

4. **Выбор источника коммита:**
   ```
   Выберите источник:
     1) test
     2) release_oe
     3) release_pe
   
   Ваш выбор [1-3]: 1
   ```

5. **Выбор коммита:**
   Отображаются последние 20 коммитов из выбранной ветки
   ```
   Введите хеш коммита для cherry-pick:
   > abc1234
   ```

6. Автоматически выполняется cherry-pick и push

#### Отправка изменений из hotfix ветки

Если вы уже в hotfix ветке и нужно отправить изменения:

```bash
git flow hotfix push
```

### Продолжение после конфликтов

#### Когда возникают конфликты

Конфликты могут возникнуть в двух местах:

1. **При cherry-pick в stable ветку** - если изменения конфликтуют с master
2. **При merge в целевую ветку** - если stable конфликтует с test/release_oe/release_pe

#### Как продолжить

1. **Разрешите конфликты** в файлах
2. **Добавьте файлы в staging:**
   ```bash
   git add <файлы>
   ```
3. **Продолжите операцию:**
   ```bash
   git flow continue
   ```

Плагин автоматически:
- Определит тип прерванной операции
- Завершит cherry-pick или merge
- Продолжит выполнение оставшихся шагов
- Вернется на исходную ветку

#### Проверка статуса

Чтобы посмотреть информацию о незавершенной операции:

```bash
git flow          # Выберите "Показать статус" в меню
# или из командной строки откройте меню и выберите опцию статуса
```

## 📚 Примеры использования

### Пример 1: Стандартная доставка в test

```bash
# 1. Вы работаете в ветке tasks/PROJ-123/TASK-456
# 2. Сделали 3 коммита
git log --oneline -3
# abc1234 Добавлена валидация
# def5678 Исправлен баг
# ghi9012 Рефакторинг кода

# 3. Запускаем delivery
git flow deliver

# 4. Выбираем 3 коммита
Сколько последних коммитов нужно довести?
> 3

# 5. Выбираем test (по умолчанию)
Куда нужно довести изменения?
> 1

# 6. Подтверждаем squash
Хотите объединить все коммиты в один (squash)?
> Y

# 7. Готово! PR ветка: tasks/PROJ-123/test_TASK-456
```

### Пример 2: Доработка с обновлением PR

```bash
# 1. PR уже создан, но нужна небольшая доработка
# 2. Делаем коммит с исправлением
git commit -m "Исправлена опечатка"

# 3. Запускаем delivery
git flow deliver

# 4. Выбираем только последний коммит
> 1

# 5. Выбираем обновление PR
Выберите действие:
  1) Обновить PR (пересоздать ветку с актуальной test)
> 1

# 6. PR автоматически обновлен!
```

### Пример 3: Продолжение после конфликта

```bash
# 1. Запустили delivery
git flow deliver

# 2. Возник конфликт при cherry-pick
ОШИБКА: Обнаружены конфликты!

Файлы с конфликтами:
src/main.js

Разрешите конфликты и выполните:
  git add <файлы>
  git flow continue

# 3. Разрешаем конфликт в редакторе
vim src/main.js

# 4. Добавляем файл
git add src/main.js

# 5. Продолжаем
git flow continue

# 6. Плагин автоматически завершает все оставшиеся шаги!
```

### Пример 4: Создание hotfix

```bash
# 1. Запускаем создание hotfix
git flow hotfix create

# 2. Выбираем PE
Выберите тип hotfix:
> 1

# 3. Указываем версию
Введите версию:
> 01.05.12.3

# 4. Указываем JIRA
Введите номер JIRA задачи:
> HOTFIX-789

# 5. Выбираем источник (test)
Выберите источник:
> 1

# 6. Указываем коммит
Введите хеш коммита для cherry-pick:
> abc1234

# 7. Готово! Hotfix ветка создана и отправлена
```

### Пример 5: Доведение до release_pe

```bash
# 1. Находимся в feature ветке
git flow deliver

# 2. Выбираем все коммиты
> all

# 3. Выбираем release_pe
Куда нужно довести изменения?
  1) test (по умолчанию)
  2) release_oe
  3) release_pe
> 3

# 4. Подтверждаем squash
> Y

# 5. PR создан для release_pe!
```

## 🔧 Решение проблем

### Проблема: Команда git flow не найдена

**Решение:**
```bash
# Проверьте, что скрипты установлены
ls -la ~/.local/bin/git-flow*

# Проверьте PATH
echo $PATH

# Добавьте в PATH если нужно
export PATH="$HOME/.local/bin:$PATH"
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
```

### Проблема: Permission denied

**Решение:**
```bash
chmod +x ~/.local/bin/git-flow*
```

### Проблема: Конфликты при продолжении

**Убедитесь что:**
1. Все конфликты разрешены
2. Файлы добавлены через `git add`
3. Не осталось маркеров конфликтов (`<<<<<<<`, `=======`, `>>>>>>>`)

**Проверка:**
```bash
# Проверить статус
git status

# Проверить наличие маркеров конфликтов
git diff --check
```

### Проблема: Неверный формат ветки

**Ошибка:**
```
ОШИБКА: Вы не в feature-ветке!
Ожидается формат: tasks/PARENT_JIRA/JIRA
```

**Решение:**
- Убедитесь, что вы в правильной ветке
- Проверьте формат названия ветки
- Используйте меню для создания новой ветки: `git flow` → "Создать новую задачу"

### Проблема: Потеряно состояние операции

Если файл `.git/git-flow-state` был случайно удален:

```bash
# Проверьте текущую операцию git
git status

# Если есть незавершенный cherry-pick
git cherry-pick --abort
# или
git cherry-pick --continue  # после разрешения конфликтов

# Если есть незавершенный merge
git merge --abort
# или
git merge --continue  # после разрешения конфликтов

# Затем заново запустите операцию
git flow deliver
```

## 📝 Лучшие практики

1. **Всегда используйте squash** в stable ветке для чистоты истории
2. **Проверяйте коммиты** перед доставкой - убедитесь что нет мусора
3. **Разрешайте конфликты внимательно** - проверяйте код после разрешения
4. **Обновляйте PR через вариант 1** для небольших доработок
5. **Используйте осмысленные сообщения** при squash
6. **Проверяйте статус** после конфликтов перед продолжением
